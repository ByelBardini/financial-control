## Estado atual

- Expo 56 / React Native 0.85 / React 19 / TypeScript 6 (strict). New Architecture ligada (default do SDK 56).
- Entry: `index.ts` (importa `./global.css`) → `App.tsx` (shell) → `RootNavigator`. Roda iOS, Android e Web. Web em http://localhost:8081.
- **Estilo: NativeWind v4.2** (Tailwind RN). Tokens do tema (cores/spacing/type scale/fontes) em `tailwind.config.js`. Tema **dark único** (`userInterfaceStyle: "dark"`).
- **Fontes:** Hanken Grotesk (headings/body) + Geist (labels) via `@expo-google-fonts`, carregadas em `useAppFonts` com gate de splash (`expo-splash-screen`).
- **Ícones:** `@expo/vector-icons` (MaterialIcons) embrulhados em `src/components/Icon.tsx` (único ponto que importa a lib; vocabulário semântico → glifo). Sem label = decorativo (oculto pro leitor de tela).
- **Marca:** logo do Pobrify (o "P" verde em `assets/logo.png`) renderizado por `src/components/BrandLogo.tsx` — **primeira e única `<Image>` do app** (RN core `Image` + `require` do asset). Aparece ao lado do wordmark "Pobrify" (login, criar conta, TopBar mobile, chip do SideNav). Decorativo por padrão (mesma a11y do `Icon`: oculto pro leitor de tela, pois o texto carrega o significado). **Ícone do app + favicon:** gerados de `assets/logo.png` sobre fundo azul `#0B1F3A` pelo script `scripts/generate-app-icons.mjs` (jimp) — cantos arredondados só no favicon (web não arredonda); iOS/Android arredondam via máscara do SO.
- **Tela Dashboard ("Pobrify") responsiva** e ligada à **API real** (React Query, dados por seção; CORS habilitado no server): em tela larga (≥1024px, web/PC) renderiza o **layout desktop** (sidebar fixa + grid enterprise de células com bordas finas + glow `expo-linear-gradient`); em tela estreita, a **pilha mobile**. **Criação de transação a partir da Início** (só criar, sem editar): a `DashboardScreen` hospeda o mesmo fluxo da tela de Transações via `useTransactionEntry` (hook compartilhado, dono do estado do mini menu + modal). No **desktop** o botão "Nova transação" do `DesktopHeader` abre o popover `NewTransactionMenu` (ancorado por `measureInWindow`, abaixo do botão); no **mobile** o `MobileDashboard` ganhou o `TransactionSpeedDial` (FAB "+"). A escolha do sentido (Receita/Despesa) abre o `TransactionFormModal` (título "Nova receita"/"Nova despesa").
- **Tela Contas ("Monitor de Sobrevivência") responsiva e ligada à API real** (React Query, dados por seção via `QuerySection`; o flip do mock pra `apiGet('/contas/...')` está feito). Contas separadas por tipo — **Bancos** (lista/cards com saldo + nota ácida), **Cartões** (cards por cartão com fatura atual + barra de uso do limite + "disponível de total" + nota ácida), **Vales/Benefícios** (cards com barra de consumo + status) e **Carteira Física** (espécie + "Confiança Financeira") — mais o **Panic Meter** (barra-gradiente), **Raio-X de Pobreza** (desktop, agregado dos cartões) e **Dica de Gestão** (reusa `DiagnosisCard` com `icon="lightbulb"`). **Sem total agregado** (não há "Patrimônio Líquido"; o endpoint `/contas/overview` foi removido): por decisão de produto a tela mostra só o saldo de cada conta + o cartão, não um balanço. Mutations (`useAccountMutations`) invalidam `['accounts']` + `['contas']` → reflete no Dashboard **e** em Contas. **Saldo só na criação** (nunca editável; muda só por transações). **Cartão não tem saldo inicial**: o campo "Saldo inicial" some quando o tipo é `credit_card` (só "Limite de crédito"), e `toNewAccountInput` zera `openingBalanceCents` p/ cartão mesmo com valor residual no estado — o saldo do cartão é só a fatura (o server rejeita `!= 0` com 400). Mockups de referência em `docs/pages/contas/` (`contas.html` / `contas-mobile.html`).
- **Tela Transações ("Terminal Financeiro") responsiva e ligada à API real** (React Query): as views vivem em `src/api/transacoes` e os hooks em `useTransacoesQueries` (chave `['transacoes', ...]`). O backend (domínio `transacoes`) filtra/pagina e deriva labels/tag/colapso/notas — o client só renderiza. **Controles funcionais (server-side, padrão de mercado)**: a `TransacoesScreen` é dona do `useTransactionFilters` (controlador: período + categorias[] + busca + from/to do custom, com `searchText` debounçado p/ `filters.query`), passado aos dois layouts. **Período = dropdown** (`PeriodFilter`): **30 Dias (default)** / 3 Meses / 6 Meses / 1 Ano / **Personalizado**; o custom revela dois `DateField` (De/Até) — **platform split**: `<input type="date">` (calendário do browser) no **web/PC** e `@react-native-community/datetimepicker` no **iOS/Android**. **Categoria = filtro multi-seleção** (`CategoryFilter` via `useCategories`/`GET /categories`): checkboxes, o modal **fica aberto** ao escolher, combina AND com tempo + busca (e OR entre as categorias no server). A lista re-busca via `getTransactionsPage(filters, page, pageSize?)` (envelope `{items,page,pageSize,total,pageCount}`); **desktop** pagina (`useTransactionsPage` + `Pagination`) e **mobile** acumula (`useTransactionsInfinite` + "Carregar mais"). **Paginação dinâmica no desktop**: a tela trava na viewport (sem scroll da página; header + fluxo fixos no topo; **só a coluna direita** Recorrências/Dívidas rola — `ScrollView` próprio). O `TransactionListPanel` mede o corpo da lista (`flex-1`, `overflow-hidden`) + a altura ocupada pelas linhas e deriva o `pageSize` por `rowsForHeight(bodyHeight, contentHeight, count)` (`src/lib/fitRows.ts`: floor da altura/linha, nunca estoura), reportado via `onRowsFit`; o `DesktopTransacoes` **trava no primeiro valor** (não recalcula no resize) e o passa ao `useTransactionsPage` (server clampa `[1,100]`, default 10 até a medição). Linha de altura uniforme (`numberOfLines={1}` no título). Estado em `FilterChips` (chip de período quando ≠ 30 Dias + um por categoria + busca, removíveis + "Limpar" + contagem). Busca menor no header desktop (`TransactionSearch compact`). Demais seções: **Fluxo de Caixa**, **Previsão de Colapso** (`PanicMeter`), **Recorrências** (cada recorrência é um **modelo**; quando a ocorrência do período corrente está pendente — `isDue` do server — a linha mostra o botão **"Registrar"** que lança a transação real via `POST /recurring-rules/{id}/register`) e **Dívidas Futuras**. **Cadastro/edição/exclusão** via **modal responsivo** `TransactionFormModal` (espelha o `AccountFormModal`: diálogo central `fade` no **PC**, bottom sheet que sobe `slide` no **mobile**; backdrop escurece e fecha). A `TransacoesScreen` hospeda o form via **`useTransactionEntry`** (hook compartilhado com a `DashboardScreen`, dono do estado `{mode, direction|id} | null` + do mini menu) — **não há rota/página** (a `NovaTransacaoScreen` foi removida). O **sentido é escolhido antes**, no mini menu: no **desktop** o botão "NOVA TRANSAÇÃO" abre um popover (`NewTransactionMenu`, ancorado abaixo do botão via `measureInWindow`); no **mobile** o **FAB "+" vira speed dial** (`TransactionSpeedDial`: expande Receita/Despesa, "+"→"×", com backdrop). A escolha abre o modal já com o sentido **travado**, e o **título é contextual** ("Nova despesa" / "Nova receita" / "Editar transação"). Tocar numa linha (`DesktopTransactionRow`/`TransactionRow` viram alvo "Editar" via `EditableCard`) abre editar pré-preenchido (`useTransaction` → `GET /transactions/{id}`) com a **conta travada** e o botão **Excluir** (confirmação em 2 passos). O modal porta o `TransactionForm` (presentacional) — **sem toggle Despesa/Receita** (o sentido vem do menu). **Tipo de lançamento** (`EntryKindSelect`, só na criação): **Único** / **Parcelado** / **Fixo** — **Parcelado some em Receita** (parcelamento é sempre despesa). Campos: **Valor** (`MoneyField`; vira "Valor da parcela" no parcelado) → **Tipo** → [parcelado] **Parcelas** (`SelectField` 2..24 + total) → **Conta** (`SelectField` **com ícone + cor da marca**, default 1ª conta) → **Categoria** (`SelectField` **com ícone**, opcional, filtrada pelo sentido) → **Descrição** (`FormField`, **opcional** — vazia vira "Despesa"/"Receita" via `descOrDefault`, pois o banco exige texto não-vazio) → **Data** ("Início" no fixo) → [fixo] **Recorrência** (`RecurrenceFields`: frequência mensal/semanal/diária/anual + término **Indefinido / Até data / Nº de vezes**). **Serialização por tipo**: único → `createTransaction`; parcelado → `createInstallmentPurchase` (valor por parcela × N, datadas mês a mês); fixo → `createRecurringRule` (**só a regra/modelo — NÃO lança transação**; cada ocorrência é registrada depois pelo botão da recorrência). As mutations (`useTransactionMutations`: create/installmentPurchase/recurringRule/**registerRecurrence**/update/delete) invalidam `['transacoes']`+`['accounts']`+`['contas']`+`['dashboard']` — **saldo é derivado**, reflete nas três telas. **Tags com significado**: a `tag` de cada linha sai de sinais reais no server (Parcelado > Fixo/Inflow Esperado > Sobrevivência/Supérfluo pela `essentialness` da categoria / Renda Extra) — não mais só income×expense. `SelectField` ganhou `icon?`/`dotColor?` por opção (conta = ícone+cor, categoria = só ícone). Dinheiro em centavos; máscara de ocultar valores (`useHideValues`). **Fora de escopo**: edição de parcelamento/recorrência (V2), materialização de ocorrências futuras (agendador), override manual de tag, atalhos de range, salvar filtros, ordenação, "salvar e adicionar outra", transferências.
- **Tela Investimentos ("Portfólio de Ilusões") responsiva e ligada à API real, com cadastro + compra/venda** (React Query, dados por seção via `QuerySection`): as views vivem em `src/api/investimentos` e os hooks em `useInvestimentosQueries` (chave `['investimentos', ...]`). **Ligada ao backend** via `apiGet('/investimentos/...')`: as views (resumo/posições/alocação/cripto) vêm prontas do server (posição **derivada** do preço médio móvel); o `investimentosSnapshot` voltou a ser **só fixture de teste**. O bloco de investimentos da **Início** (`/investments`, `/dashboard/investments-summary`, `investidoCents`) agora **deriva desta mesma carteira** no server (não são mais stubs); o `/dashboard/ticker` foi removido. **Valoração manual, sem cotação ao vivo**: cada posição mostra **Investido → Valor Atual → Ganho/Perda** (R$ e %) — a "variação" é o valor atual informado menos o total investido (sem preço-por-unidade nem variação 24h ao vivo, que pressupõem market data que não temos). **Cripto é um pilar à parte** (`CryptoSection`): NÃO entra no total nem na alocação do portfólio geral; tem subtotal e bloco próprios ("O Circo da Volatilidade") e cada card tem um gráfico de linha/área interativo (`PriceSparkline`, com `react-native-svg`): crosshair + tooltip que segue o cursor (hover no PC, arrastar no toque) mostrando **data + valor** do ponto (`labels` opcional no `PriceSparkline` + rótulos de período via `lib/chartDate`) — série `{date, priceCents}[]` do **histórico de preço** do backend (`investment_prices`; não é cotação ao vivo). O mesmo `PriceSparkline` aparece no **detalhe de qualquer ativo** (`AssetHistorySection` no `AssetDetailModal`, via `usePriceHistory` + toggle de período 1M/6M/1A). Seções: **Resumo do portfólio geral** (`PortfolioHero`: patrimônio + ganho/perda acumulado — só Ações/FIIs/Renda Fixa), **Alocação por classe** (`AllocationBar`: barra segmentada + legenda, cripto fora), **Evolução do Patrimônio** (`EvolutionSection` + `PortfolioEvolutionChart`: 2 linhas no mesmo eixo — **valor atual × investido** (legenda nesses termos, alinhada à tabela de posições; o gap = ganho/perda); tooltip mostra **data + os dois valores** e há rótulos de período (início … fim, via `lib/chartDate`); `react-native-svg` reusando a geometria de `lib/cryptoChart#chartPointsIn`; vem do `GET /investimentos/evolution` via `usePortfolioEvolution(range)` com **forward-fill** no server (sem preço no ledger, cai no `current_price`); cripto fora — é o gráfico de "valorizou ou não?"; estado vazio "Sem histórico ainda"), **Posições** ("Registro de Quedas" — no desktop é tabela com colunas Ativo | Investido | Valor Atual | Ganho/Perda via `PositionRow variant="row"`; no mobile, cards via `variant="card"`), **Cripto à parte** e **Avaliação de Risco** — resumo do desempenho **derivado do lucro/perda geral** (geral + cripto) via `lib/investmentRisk#assessRisk` (status verde no lucro, vermelho no prejuízo; não é cravado à mão). `RiskAssessmentCard` é um card no estilo do mockup (ícone de alerta + status grande colorido + resumo + frase ácida) — **NÃO usa `PanicMeter`** (esse segue só na tela de Contas). Desktop = sidebar + header (título "Investimentos" + ocultar valores + **"Novo ativo"**) + grid 2/3 (portfólio geral) / 1/3 (cripto + risco) com `border-grid-line` + brilho `expo-linear-gradient`; mobile = TopBar + pilha + BottomNav + **FAB "Novo ativo"**. **Cadastro + compra/venda no front** (modais responsivos via `ModalSheet`, espelham o `AccountFormModal`): a `InvestimentosScreen` é dona do estado dos modais (união `createAsset|detail|editAsset|trade`). O FAB/"Novo ativo" abre o `AssetFormModal` (criar); tocar numa posição/cripto (`PositionRow`/`CryptoCard` viram alvo via `EditableCard`) abre o `AssetDetailModal` (posição + operações passadas, cada uma excluível, + **Comprar mais / Vender / Editar**); comprar/vender abre o `TradeModal` (lado fixo) — o **preço unitário vem pré-preenchido do ativo** (editável) e a entrada é por **quantidade** (total sai sozinho) ou — toggle **só em cripto**, que abre nele — por **valor em R$** (a quantidade sai sozinha), sempre com **conta de liquidação obrigatória**. As mutations (`useInvestmentMutations`) invalidam `['investimentos']`+`['accounts']`+`['contas']`+`['transacoes']`+`['dashboard']` (a operação mexe no saldo e cria a transação `kind='investment'`). Dinheiro em centavos; **quantidade fracionária como string decimal** (até 8 casas); máscara de ocultar valores (`useHideValues`). Mockups de referência em `docs/pages/investimentos/` (`investimentos.html` / `investimentos-mobile.html`). **Fora de escopo (v1 do front)**: cotação ao vivo (cripto/B3).

- **Auth real (multi-usuário):** o `AuthProvider` (`src/auth/AuthContext.tsx`) é dono da sessão — no mount restaura o token do storage e valida com `GET /auth/me`; expõe `status` (`loading`/`authenticated`/`unauthenticated`), `user`, `signIn`, `signOut` (via `useAuth`). Layout via `AuthLayout` (split desktop ≥1024px / empilhado mobile com `KeyboardAvoidingView`). Mockups de referência (HTML/Tailwind estático, fora do runtime) em `docs/pages/login/`: `login.html` (split desktop) e `login-mobile.html` (empilhado mobile).

## Estrutura `src/`

- `screens/` — `LoginScreen` (e-mail+senha, valida no client) e `CreateAccountScreen` (só e-mail + aviso de aprovação) compõem o `AuthLayout`. `DashboardScreen`, `ContasScreen`, `TransacoesScreen` e `InvestimentosScreen` só escolhem o layout via `useIsDesktop`, compartilham o estado de máscara e repassam `route`/`onNavigate`/`onLogout?` aos layouts (a de **Investimentos** é dona do estado dos **modais de ativo/operação** — união discriminada `createAsset|detail|editAsset|trade`: o FAB/"Novo ativo" cadastra, tocar num card abre o **detalhe** e o detalhe transita pra comprar/vender/editar; hospeda `AssetFormModal`/`AssetDetailModal`/`TradeModal`). O **lançamento de transação** (criar/editar) é um **modal responsivo** (`TransactionFormModal`), **não uma página**: `TransacoesScreen` **e** `DashboardScreen` hospedam o estado via `useTransactionEntry` (abrir pelo mini menu/speed dial → criar; tocar numa linha → editar, só em Transações). A antiga `NovaTransacaoScreen` (rota `'nova-transacao'`) foi **removida**. `MobileDashboard`/`DesktopDashboard` (API real), `MobileContas`/`DesktopContas` (API real) `MobileTransacoes`/`DesktopTransacoes` (**mock-backed via `src/api/transacoes`**) e `MobileInvestimentos`/`DesktopInvestimentos` (**API real via `src/api/investimentos`**; views por seção + cadastro/compra/venda nos modais) buscam os dados **por seção** (cada card é um `useQuery`) e usam `QuerySection`/`QuerySection2` (gate skeleton/erro/dados) — os componentes de seção seguem presentacionais (prop-driven). O shell (QueryClientProvider, SafeAreaProvider, gate de fontes, StatusBar) vive no `App.tsx`, deixando as telas portáveis pra um futuro Expo Router.

## Convenções

- **Componentizado, sem monolitos.** Um componente por arquivo; tela só compõe; lógica/estado em hooks. Arquivo perto de 500 linhas = quebrar.
- Componentes funcionais + hooks. **Exceção:** `ErrorBoundary` é class component (React 19 ainda exige classe pra `getDerivedStateFromError`).
- `strict` no TS; sem `any`.
- Dinheiro: nunca aritmética com `number` cru (ver `money.md`); formate só na borda via `lib/money.ts#formatBRL`.
- **Acessibilidade é padrão:** toggles com `accessibilityRole`/estado, alvos de toque ≥44px, ícones decorativos ocultos, barras com `accessibilityValue`, valores mascarados com `accessibilityLabel="valor oculto"`.
- **Camada de dados:** toda chamada HTTP vive em `src/api` (`client.ts#apiGet` é o único `fetch`; `dashboard.ts` tem uma função por endpoint). Nenhum `.tsx` chama API. React Query (`@tanstack/react-query`) provê cache/loading/erro via hooks por recurso em `src/hooks/useDashboardQueries.ts`. Base URL: `EXPO_PUBLIC_API_URL` (default `http://localhost:8080`).

- Jest + `jest-expo` + `@testing-library/react-native` v14. Config em `client/jest.config.js` (estende o preset do jest-expo: libera `nativewind` no `transformIgnorePatterns` e carrega `jest.setup.ts`). Testes em `client/__tests__/` espelhando `src/`. Rode: `npm run test:client`.

- Componentes testam texto/role/estado, nunca `style`/`className` (NativeWind não aplica estilo no jest). `jest.setup.ts` mocka fontes, splash, SafeAreaProvider e **AsyncStorage** (`@react-native-async-storage/async-storage/jest/async-storage-mock`). `jest.config.js` usa `testTimeout: 15000` (a suíte cresceu; telas pesadas passavam dos 5s default por contenção de CPU sob paralelismo, não por bug).

## Decisões resolvidas

- **Navegação/sessão:** `RootNavigator` é o **gate** de `useAuth` (sem lib de routing) — sem sessão→Login/Criar conta, com sessão→`AuthenticatedApp`. Auth é **real** (JWT no header `Authorization`; `POST /auth/login` + `GET /auth/me`; token persistido no AsyncStorage). A navegação interna **agora alterna Dashboard↔Transações↔Contas** via estado local no `AuthenticatedApp` (`AppRoute`), que desce `currentRoute`/`onNavigate` pra sidebar/bottom-nav (itens "Início"/"Transações"/"Contas" ativos e navegáveis; resto decorativo). Candidato pra depois: **Expo Router** (shell isolado no `App.tsx`).
- **Estado/queries:** React Query adotado. Dados por recurso em `src/hooks/useDashboardQueries.ts`, chamadas em `src/api`, loading/erro **por seção** via `QuerySection`. Base URL em `EXPO_PUBLIC_API_URL` (build-time; reinicie o Expo ao mudar; device físico usa o IP da LAN).
